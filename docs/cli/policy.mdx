---

The `hexgate policy` subcommands author, inspect, and compile policies without a
running platform. See [WASM bundles](/policy/wasm-bundles) for what `build`
produces and [signing](/policy/signing) for `keygen`.

```bash
# Validate a policy.yaml without the network — parse + check every constraint
hexgate policy validate policy.yaml

# See the Rego your YAML compiles to (stdout)
hexgate policy show-rego policy.yaml

# Dry-run a single decision. --engine wasm compiles + evaluates in wasmtime
# (matching production); the default pydantic engine needs no opa.
hexgate policy test policy.yaml --role billing --tool refund_order \
    --args '{"amount": 200, "currency": "USD"}' --engine wasm

# Dry-run a multi-role caller: most permissive wins, and the granting role
# is printed. Use this to check what a caller with several roles can do.
hexgate policy test policy.yaml --roles support,billing --tool refund_order \
    --args '{"amount": 200, "currency": "USD"}'

# Compile a bundle: writes {stem}.yaml + .rego + .wasm + .bundle.json
hexgate policy build policy.yaml --out ./bundle

# Sign it with a local key: also writes {stem}.bundle.json.sig
hexgate policy build policy.yaml --out ./bundle --sign-key ./keys/dev.private

# Generate an Ed25519 keypair for signing bundles
hexgate policy keygen --out ./keys/dev          # → dev.private (0600) + dev.public
hexgate policy keygen --out ./keys/dev --force  # overwrite an existing pair

# Link a policies/ module tree into the one policy the engines enforce
hexgate policy resolve --dir .

# Lint the same tree for grants that never fire, duplicates and drift
hexgate policy check --dir .
```

## Prerequisite — `opa`

The WASM compile step shells out to the [Open Policy
Agent](https://www.openpolicyagent.org/) binary. Install it once:

```bash
brew install opa            # macOS
# or see https://www.openpolicyagent.org/docs/latest/#running-opa
```

Without `opa` on `PATH`, `hexgate policy build --no-wasm` still emits the yaml +
rego (no `.wasm`), and the pydantic engine keeps working. Override the binary
location with `HEXGATE_OPA_BIN`.

## Reading a denied `test`

On a denied decision, `test` prints the reason; the wasm engine additionally
lists each violated constraint string verbatim:

```text
✗ DENY · billing → refund_order({"amount": 700})
  reason: Policy denied tool "refund_order": args.amount <= 500
  violations:
    • args.amount <= 500
```

## Multi-role dry-runs (`--roles`)

`--role` evaluates one role; `--roles a,b` evaluates a whole set exactly as the
runtime does, and the output names the role that granted the call:

```bash
$ hexgate policy test policy.yaml --roles support,billing --tool refund_order --args '{"amount": 200}'
✓ ALLOW · [support, billing] → refund_order({"amount": 200})
  granted by: billing
```

How the two flags treat undefined names and an empty set, and the 32-role cap,
are in [Validation and dry-run rules](/policy/testing-a-policy#several-roles-in-a-dry-run).

## Validating

`validate` checks the policy alone, and against the agent's code when you pass
its manifest. Every check it runs and at which severity is in
[Validation and dry-run rules](/policy/testing-a-policy#what-validation-checks):

```bash
hexgate policy validate policy.yaml --max-severity warning   # non-zero on any warning
hexgate policy validate policy.yaml --manifest manifest.json
hexgate policy validate policy.yaml --manifest manifest.json --max-severity warning
```

## Testing `ctx.*` attribute rules

Constraints can filter on caller attributes via `ctx.*` (see
[constraints](/policy/constraints)). Pass them to `test` with `--attributes`, a
JSON object so numbers and booleans keep their type:

```bash
hexgate policy test policy.yaml --role billing --tool refund_order \
    --args '{"amount": 30}' \
    --attributes '{"department": "finance", "clearance_level": 3}'
```

How a key you don't pass is treated is in
[Validation and dry-run rules](/policy/testing-a-policy#missing-values-in-a-dry-run).

## Testing `run.*` and usage rules

`--run-facts` feeds `run.*` constraints (this run's counters),
`--agent-usage` feeds `agent_usage.*` constraints (this agent across runs) and
`--user-usage` feeds `user_usage.*` constraints (one end user across agents).
Each takes a JSON object; how a path you don't pass is read is in
[Validation and dry-run rules](/policy/testing-a-policy#missing-values-in-a-dry-run).
To dry-run a limit at its threshold:

```bash
hexgate policy test policy.yaml --role default --tool send_email \
    --run-facts '{"tool_calls": 20}'

hexgate policy test policy.yaml --role default --tool agent.run \
    --args '{"agent": "billing"}' --agent-usage '{"invocations_1h": 100}'

hexgate policy test policy.yaml --role default --tool agent.run \
    --args '{"agent": "billing"}' --user-usage '{"invocations_1h": 50}'
```

See [constraints](/policy/constraints) for the paths each one exposes.

## Policy modules: `resolve` and `check`

A project can split its policy into modules under `policies/`: boundaries in
`policies/boundaries/` set ceilings and denies, capabilities in
`policies/capabilities/` grant. The linker folds them into one effective policy
(fences intersect, grants union, denies win), and that policy is what compiles to
Rego and WASM. Two commands work on the tree.

### `resolve`: see what will be enforced

`resolve` links the modules and prints the effective policy, with the layers it
read and any grant a ceiling shadows. With this tree:

```yaml
# policies/boundaries/org.yaml
default_policy: { mode: deny }
tools:
  refund_order:
    mode: allow
    constraints:
      - args.amount <= 500
```

```yaml
# policies/capabilities/support.yaml
tools:
  refund_order: { mode: allow }
  send_email: { mode: allow }
```

```text
$ hexgate policy resolve --dir .

[default] layers (resolution order):
  [boundary  ] org  (policies/boundaries/org.yaml)
  [capability] support  (policies/capabilities/support.yaml)
  shadowed (ineligible under a ceiling):
    send_email  ← org (policies/boundaries/org.yaml)
version: 1
inherits: []
is_mixin: false
default_policy:
  mode: deny
  constraints: []
constraints: []
tools:
  refund_order:
    mode: allow
    constraints:
    - args.amount <= 500
consts: {}
admission: null
agents: {}
skills: {}
_resolved: true
```

`send_email` is granted by `support` but the `org` ceiling never lists it, so it
is shadowed and absent from the result.

| Flag | What it does |
|---|---|
| `--dir PATH` | Repo root holding the `policies/` tree (default: the current directory). |
| `--file PATH` | Resolve one file written in the module authoring format (the one with boundary, reach and import blocks) instead of a tree. A plain `policy.yaml` like the ones above fails with a link error. Can't be combined with `--dir`. |
| `--agent NAME` | The executing agent to resolve for, which selects that agent's column. |
| `--role NAME` | Print only this role's effective policy. Without it, a project with a `roles.yaml` prints every role. |
| `-o PATH`, `--output PATH` | Write the effective policy YAML to a file instead of stdout. |

### `check`: lint the modules

`check` links the same tree and reports mistakes that don't stop it from
composing. On the tree above:

```text
$ hexgate policy check --dir .
  (drift checks skipped — pass --manifest to enable them)
! [dead-grant] [default] 'support' grants 'send_email' but boundary 'org' (a ceiling) never permits it — this grant never fires (policies/capabilities/support.yaml)
```

It reports a capability grant a ceiling makes dead, a duplicate grant, and a
constraint path no call sets. With `--manifest`, it also reports rules on a tool,
skill or argument the agent's code doesn't have, as `validate` does.

| Flag | What it does |
|---|---|
| `--dir PATH` | Repo root holding the `policies/` tree (default: the current directory). |
| `--role NAME` | Only lint this role, plus project-level lints. |
| `--manifest PATH` | The agent's manifest JSON. Turns on the drift checks. |
| `--max-severity LEVEL` | Exit non-zero when any lint is at or above this level (default `error`). A dead grant is a `warning`, so the run above exits 0, and exits 1 with `--max-severity warning`. A tree that fails to link exits 1. |

Use `check --max-severity warning` in CI to keep dead and duplicate grants out of
the tree.
