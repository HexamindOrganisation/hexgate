The `hexgate policy` subcommands author, inspect, and compile policies without a
running platform. See [WASM bundles](/policy/wasm-bundles) for what `build`
produces and [signing](/policy/signing) for `keygen`.

```bash
# Validate a policy.yaml without the network — parse + check every constraint
hexgate policy validate policy.yaml

# See the Rego your YAML compiles to (stdout)
hexgate policy show-rego policy.yaml

# Dry-run a single decision. --engine wasm compiles + evaluates in wasmtime
# (matching production); the default pydantic engine needs no opa.
hexgate policy test policy.yaml --role billing --tool refund_order \
    --args '{"amount": 200, "currency": "USD"}' --engine wasm

# Compile a bundle: writes {stem}.yaml + .rego + .wasm + .bundle.json
hexgate policy build policy.yaml --out ./bundle

# Generate an Ed25519 keypair for signing bundles
hexgate policy keygen --out ./keys/dev          # → dev.private (0600) + dev.public
```

## Prerequisite — `opa`

The WASM compile step shells out to the [Open Policy
Agent](https://www.openpolicyagent.org/) binary. Install it once:

```bash
brew install opa            # macOS
# or see https://www.openpolicyagent.org/docs/latest/#running-opa
```

Without `opa` on `PATH`, `hexgate policy build --no-wasm` still emits the yaml +
rego (no `.wasm`), and the pydantic engine keeps working. Override the binary
location with `HEXGATE_OPA_BIN`.

## Reading a denied `test`

On a denied decision, `test` prints the reason; the wasm engine additionally
lists each violated constraint string verbatim:

```text
✗ DENY · billing → refund_order({"amount": 700})
  reason: Policy denied tool "refund_order": args.amount <= 500
  violations:
    • args.amount <= 500
```

## Attributes (`ctx.*`) and the trusted tier

Constraints can filter on the caller's ABAC attributes through the `ctx.*`
namespace, alongside `role`, `tool`, and `args.*`:

```yaml
tools:
  refund_order:
    mode: allow
    constraints:
      - "ctx.department == \"finance\""
      - "ctx.clearance_level >= 3"
```

Attributes come from the request scope (`HexgateContext(attributes={...})`). By
default they are **advisory** — read from the process contextvar, so they are
spoofable and are meant for dev/local filtering, never a production `deny` gate.

To let an attribute gate a real decision, declare it **trusted**:

```yaml
trusted_attributes:
  - clearance_level
```

A trusted key is signed into the per-request Biscuit and read back from it. The
enforcer ignores any contextvar value for that key and uses only the token
value; a trusted key absent from the token **fails closed** (any constraint on
it denies). Trust is deployment-wide — a key trusted in one role is trusted
everywhere. Values must be scalar (`str` / `int` / `bool`); list-valued trusted
attributes are not supported yet (a list value is dropped and fails closed).

**What "trusted" guarantees.** It means the value was *asserted by the holder of
your project API key (your backend) and is verifiable downstream by the
platform* — **not** that it's unforgeable inside your own process. Populate
attribute values from trusted server-side data (an IdP/session), never raw
client input, exactly as you would `user_roles`. When the SDK signs the token
in-process from the contextvar, the audit trail records those values as
`self_asserted` rather than `verified`; a value is `verified` only when it
arrived on a token the process received from an external signer.

Trusted attributes resolve only on the **agent-invoke** path today. The egress
gate and the framework adapters bind the request scope but not the verified
token, so a trusted `ctx.*` key is absent there and fails closed — advisory
`ctx.*` keys still work on every path. Declare a key trusted only when the tools
it gates run on the agent-invoke path.

`hexgate policy test --attributes '{...}'` evaluates the raw engine below the
enforcement trust boundary, so it treats every `ctx.*` key as present — it shows
the **advisory** semantics. The trusted/verified distinction only applies at
enforcement time, with a real signed token.
