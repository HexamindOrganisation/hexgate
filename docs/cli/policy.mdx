The `hexgate policy` subcommands author, inspect, and compile policies without a
running platform. See [WASM bundles](/policy/wasm-bundles) for what `build`
produces and [signing](/policy/signing) for `keygen`.

```bash
# Validate a policy.yaml without the network — parse + check every constraint
hexgate policy validate policy.yaml

# See the Rego your YAML compiles to (stdout)
hexgate policy show-rego policy.yaml

# Dry-run a single decision. --engine wasm compiles + evaluates in wasmtime
# (matching production); the default pydantic engine needs no opa.
hexgate policy test policy.yaml --role billing --tool refund_order \
    --args '{"amount": 200, "currency": "USD"}' --engine wasm

# Dry-run a multi-role caller: most permissive wins, and the granting role
# is printed. Use this to check what a caller with several roles can do.
hexgate policy test policy.yaml --roles support,billing --tool refund_order \
    --args '{"amount": 200, "currency": "USD"}'

# Compile a bundle: writes {stem}.yaml + .rego + .wasm + .bundle.json
hexgate policy build policy.yaml --out ./bundle

# Generate an Ed25519 keypair for signing bundles
hexgate policy keygen --out ./keys/dev          # → dev.private (0600) + dev.public
```

## Prerequisite — `opa`

The WASM compile step shells out to the [Open Policy
Agent](https://www.openpolicyagent.org/) binary. Install it once:

```bash
brew install opa            # macOS
# or see https://www.openpolicyagent.org/docs/latest/#running-opa
```

Without `opa` on `PATH`, `hexgate policy build --no-wasm` still emits the yaml +
rego (no `.wasm`), and the pydantic engine keeps working. Override the binary
location with `HEXGATE_OPA_BIN`.

## Reading a denied `test`

On a denied decision, `test` prints the reason; the wasm engine additionally
lists each violated constraint string verbatim:

```text
✗ DENY · billing → refund_order({"amount": 700})
  reason: Policy denied tool "refund_order": args.amount <= 500
  violations:
    • args.amount <= 500
```

## Multi-role dry-runs (`--roles`)

`--role` evaluates one role; `--roles a,b` evaluates a whole set exactly as the
runtime does — every role is evaluated and the most permissive outcome wins, so
the output also names the role that granted the call:

```bash
$ hexgate policy test policy.yaml --roles support,billing --tool refund_order --args '{"amount": 200}'
✓ ALLOW · [support, billing] → refund_order({"amount": 200})
  granted by: billing
```

The two flags differ on undefined names, deliberately:

- `--role nope` **fails** — a single undefined role is almost always a typo.
- `--roles support,nope` **warns and continues**, evaluating `nope` against the
  `default` policy. That is what happens at runtime, and a dry-run that refused
  would disagree with production.
- `--roles ""` **fails** — an empty set names no roles. Scripting this as
  `--roles "$ROLES"` with an unset variable would otherwise dry-run the
  `default` policy and exit 0, passing CI while asserting nothing. Pass
  `--roles default` if the fallback policy is what you meant to test.

At most 32 distinct roles are evaluated, matching the enforcer; past that the
dry-run warns on stderr and evaluates the first 32, as production would.

That fallback is also why `default` should stay least-privilege — see
[request context](/concepts/user-scope). `hexgate policy validate` warns when the
`default` role grants something no named role grants, and when the document
declares roles but never names one `default` (so one of them silently becomes
the fallback):

```bash
hexgate policy validate policy.yaml --max-severity warning   # non-zero on either warning
```

`validate` also fails when roles set different `guards:` settings, since the
runtime builds one guard pipeline per agent. Pass the agent's manifest to check
the policy against its code too: a `guards:` rule naming a guard the agent
doesn't declare, and a tool or argument the agent doesn't have:

```bash
hexgate policy validate policy.yaml --manifest manifest.json
```

## Testing `ctx.*` attribute rules

Constraints can filter on caller attributes via `ctx.*` (see
[constraints](/policy/constraints)). Pass them to `test` with `--attributes`, a
JSON object so numbers and booleans keep their type:

```bash
hexgate policy test policy.yaml --role billing --tool refund_order \
    --args '{"amount": 30}' \
    --attributes '{"department": "finance", "clearance_level": 3}'
```

A `ctx.*` key you don't pass is treated as missing and fails closed, exactly as
at runtime when the request scope omits it.
