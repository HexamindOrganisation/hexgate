These are the rules behind validating a policy and dry-running a decision,
whatever runs them: the `hexgate policy` CLI (commands and flags in
[hexgate policy](/cli/policy)) or the MCP server's tools.

## Several roles in a dry-run

A caller holding several roles is evaluated as the runtime does: every role is
evaluated and the most permissive outcome wins, `allow` over
`approval_required` over `deny` (see
[Roles and caller attributes](/policy/roles-and-attributes#multiple-roles-most-permissive-wins)).
The runtime evaluates at most 32 distinct roles per caller.

## Missing values in a dry-run

A `ctx.*` key you don't pass is treated as missing and fails closed, exactly as
at runtime when the request scope omits it.

## What validation checks

`default` is the fallback for undefined role names, which is why it should stay
least-privilege. Validation warns when the `default` role grants something no
named role grants, and when the document declares roles but never names one
`default` (so one of them silently becomes the fallback). With
`--max-severity warning`, either warning fails validation.

Validation also fails when roles set different `guards:` settings, since the
runtime builds one guard pipeline per agent.

It flags a constraint path no call ever sets (`unknown-root`): one that doesn't
start with `args.`, `ctx.`, `run.`, `agent_usage.` or `user_usage.`, such as
`user.department == "finance"`, or one that dots into `role` or `tool`, which are
plain strings. The path is always
missing, so the comparison is always false: a `warning`, or an `error` under an
odd number of `not`, where it is always true and the fence never fires.

It also flags an `agent_usage.*` or `user_usage.*` cap under an odd number of `not`
(`negated-usage-cap`), such as `not (agent_usage.denials_5m >= 5)` or a boundary
deny on `agent_usage.denials_5m >= 5`, which the linker wraps in `not`. Under
`usage: {on_unavailable: deny}` a value the platform can't supply is missing, so
the cap is true and the call passes. It is an `error` when the policy sets
`on_unavailable: deny`, and a `warning` on a module, which can't know the
agent's fail mode. Write the cap as a plain comparison: `agent_usage.denials_5m < 5`.

### Against the agent's manifest

Checked against the agent's manifest, at the default `--max-severity error`,
these fail validation:

- a `guards:` rule naming a guard the agent doesn't declare (`unknown-guard`),
  or one two of its guards share (`ambiguous-guard`);
- a rule on a tool or argument the agent doesn't have that leaves the real tool
  less restricted than intended (`unknown-tool` / `unknown-arg` at `error`).

The rest of the drift is printed but passes: a grant that never fires or an
argument typo that fails closed is a `warning`, and a deny on a missing tool is
`info` when the role's default already denies it. A `skills:` rule on a skill
the agent doesn't declare (`unknown-skill`) is a `warning`, or `info` for a deny:
an unlisted skill is denied either way. It is only checked when the manifest
lists the agent's skills; a manifest with no `skills` field skips it. With
`--max-severity warning`, the warnings fail too.

## The arguments each gate passes

An `admission`, `agents` or `skills` rule's `args.*` are checked against what
its gate passes: `agent` for admission; `agent`, `target` and `via` for reach;
`skill`, `via`, `file_path` and `content_hash` for a skill, plus `script_args`,
`short_options` and `positional_args` for a script.
