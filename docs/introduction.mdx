**You already have an agent. Now you want to control it.**

Your agent can call tools that move money, change records or send email. It will
call them for anyone who asks, with any arguments the model comes up with.
Nothing in the agent's code knows *who* is asking, and nothing caps *what* they
can do.

**Hexgate is runtime authorization for AI agents.** On every tool call it decides
whether **this end user**, acting in **this role**, may run **this tool** with
**these arguments**, and returns `allow`, `deny` or `approval_required`. You wrap
your existing OpenAI Agents, LangChain, Google ADK or Pydantic AI agent; you
don't rewrite it.

```text
  end user (id + role)  ×  tool call (name + args)  ──►  allow · deny · approval
```

## Same request, different answer

Authorization isn't a property of the agent. It's a property of *who is calling*
and *what they're trying to do*. A support rep and a billing lead can use the
exact same agent and the exact same `refund_order` tool, yet get different
answers, because a **policy** maps roles to tools to argument limits:

{/* This refund_order policy is copied by hand in README.md, docs/introduction.mdx, docs/quickstart.mdx, docs/snippets/policy-decider.jsx and platform/dashboard/src/components/quickstart/content.ts: keep them in sync */}
```yaml policy.yaml
roles:
  support:                       # front-line: small USD refunds only
    default_policy: { mode: deny }
    tools:
      refund_order:
        mode: allow
        constraints:
          - args.amount <= 50
          - args.currency == "USD"
      issue_credit:                # support can request; a human confirms
        mode: approval_required
  billing:                       # larger refunds, major currencies
    default_policy: { mode: deny }
    tools:
      refund_order:
        mode: allow
        constraints:
          - args.amount <= 500
          - args.currency in ["USD", "EUR"]
```

The **same** `refund_order($400)` call resolves differently per caller:

| Caller | Tool call | Decision | Why |
|---|---|---|---|
| `support` | `refund_order(amount=400, currency="USD")` | ✗ **deny** | over support's `amount <= 50` cap |
| `billing` | `refund_order(amount=400, currency="EUR")` | ✓ **allow** | within billing's `amount <= 500` |
| `support` | `issue_credit(amount=50)` | ⚠ **approval_required** | needs a human's OK |

The caps live in the policy, **outside the model**, so a prompt-injected or
confused agent can't talk its way past `amount <= 500`. It never sees the result
of a denied call; it gets a `[policy_denied]` marker it can recover from.

## A policy needs a home

A YAML file on its own enforces nothing. To trust it in production you need the
running agent to load it and check every call, one version shared by your laptop
and production, a way to change a limit without a redeploy, and a record of every
refusal. That's what the **Hexgate platform** is: a registry for your agents'
policies.

## What Hexgate is

Hexgate is two things that move together:

- **`hexgate`, the SDK.** A Python runtime that intercepts every tool call and
  runs it through a `PolicyEnforcer`, resolving the caller's role at call time
  and returning a typed `Decision`. It wraps your existing agent without
  rewriting it.
- **The Hexgate platform.** A control plane and dashboard for editing policy in
  a browser, minting per-project API keys, watching live decisions stream from a
  serving agent, and shipping signed policy bundles to production. Use
  **[Hexgate Cloud](/platform/hosted)** (hosted: set one env var) or
  [self-host it](/platform/control-plane).

Two things feed the decision, and one thing records it:

- The **end user's identity and role** are a decision input. Carried per request
  via [`HexgateContext`](/concepts/user-scope), they select which role's rules
  apply.
- The **policy** supplies the rules: a [YAML file or signed WASM
  bundle](/policy/wasm-bundles), loaded from the platform or locally.
- Every decision is written to an [**audit trail**](/concepts/audit-trail): who
  called what, and whether it was allowed.

## The decision path

```text
     end user (id + role)          tool call (name + args)
              └───────────────┬────────────────┘
                              ▼
                PolicyEnforcer.decide()  ◄──  policy
                              ▼                (signed bundle from the platform,
              allow  ·  deny  ·  approval        or local YAML / bundle)
                              │
                              ▼
        audit log: who called what, and whether it was allowed
```
